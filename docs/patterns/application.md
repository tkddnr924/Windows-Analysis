# 앱 구조와 데이터 관리

- 현 구조(호스트 등록 → 파싱 → 분석 뷰)는 유지한다. 화면 구조를 변경할 때도 기존
  기능, 데이터 보존, 필터·페이지네이션의 의미를 깨지 않는다.
- 케이스 폴더(`cases/`)는 내부 저장 구조로 유지한다. 화면에서 다중 케이스 관리 UI는
  노출하지 않으며, 실행 시 케이스 이름은 `CASE_시간` 형식으로 자동 생성한다.
- **앱이 만드는 모든 데이터는 `cases/` 안에 둔다(2026-09-10 사용자 확정).** 프로그램을
  쓰면서 남는 흔적 자체는 허용하되, 산출물이 사용자 프로필 등 `cases/` 밖으로
  흩어지면 안 된다. Tauri는 Windows/Linux에서 WebView2 사용자 데이터 폴더를 지정하지
  않으면 `%LOCALAPPDATA%\<identifier>\EBWebView\`를 강제로 만들므로, `main.rs`의
  `webview_data_dir()`로 `cases/.webview`(재정의: `WINA_WEBVIEW_DIR`)에 고정한다.
  이 경로를 적용하려면 창을 `.setup()`에서 만들어야 하므로 `tauri.conf.json`의 `main`
  창은 `"create": false`를 유지한다. 새 설정·캐시 저장소도 같은 규칙을 따른다.
  `cases/` 루트에 앱 내부 폴더가 생겨도 호스트 목록·레거시 마이그레이션이 이를
  호스트로 취급하지 않는 것은 `case_store::tests::app_internal_directories_at_cases_root_are_not_hosts`로
  검증한다. Windows에서 `cases/.webview/EBWebView\`가 생기는지는 개발 환경(macOS,
  WKWebView)에서 확인할 수 없어 미검증으로 남긴다.
- 케이스/호스트 등록 같은 좁은 작업 화면은 작은 창, 결과 분석 뷰는 큰 창을 쓰며
  전환 시 창을 화면 중앙에 배치한다.
- 큰 데이터는 UI 메모리에 한꺼번에 적재하지 않는다. DB 쿼리·서버/API 페이지네이션을
  사용하고, 통계는 현재 페이지가 아니라 활성 기간 필터의 전체 데이터로 계산한다.
  **확정 예외:** `_OVERVIEW` 파생 개요 뷰는 세션 묶음·건수 집계에 전체 행이 필요해
  전량 로드를 유지한다(13차 리뷰 라운드 사용자 확정). 진짜 대용량인 원본 테이블만
  청크/페이지 경로를 쓴다.
- 기간 필터는 모든 관련 뷰(브라우저, AI 대화, 타임라인 등)에 동일하게 적용한다.
  기간 내 데이터가 없으면 빈 화면 대신 명확한 안내를 표시한다.
  **확정 예외:** 레지스트리 특이사항 뷰는 전역 기간 필터 대신 뷰 자체 날짜 필터를
  쓴다 — 레지스트리 시각은 마지막 기록 시각이라 사고 창과 어긋나는 일이 많다
  (13차 리뷰 라운드 사용자 확정).
- 새로고침은 현재 선택 호스트·필터·뷰 상태를 안전하게 다시 불러와야 하며, 저장된
  호스트/케이스 데이터를 삭제하거나 초기화하지 않는다.
- 아이콘은 장식으로 사용하지 않는다. 접기, 펼치기, 로딩, 파일 선택, 실행처럼 행동을
  명확히 하는 경우에만 MUI 아이콘을 쓴다. 이모지로 UI 의미를 표현하지 않는다.
- 뷰에서 해당 아티팩트에 대한 설명/안내 문구 등은 필요 없음
