# 파싱 아키텍처와 데이터 보존

### 파싱 아키텍처 (사용자 확정 — 필수 준수)

파싱은 다음 3단계로 진행한다. 이 구조를 임의로 되돌리지 않는다.
파싱 중 오류·손상 데이터는 실패로 기록하고 다음 아티팩트로 넘어간다(실패 기록 = 스킵과
같은 의미. 파서는 완벽하게 구현되어 있다는 전제이므로 오류·손상은 원본 문제로 판정).

1. **전 아티팩트 파일 목록화 → 그다음 파싱.**
   호스트(=수집 디렉터리) 안에서 이 도구가 지원하는 모든 아티팩트의 대상
   파일을 **모두 먼저 목록화(계획)** 한 뒤 파싱에 들어간다.
   "아티팩트#1 목록화→파싱→아티팩트#2 목록화→파싱" 식으로 아티팩트마다 목록화와
   파싱을 번갈아 하지 않는다.

2. **파싱 결과 == 원본 데이터 (완전 보존).**
   각 아티팩트는 원본이 담고 있는 모든 데이터를 최적의 방식으로 한 번에 파싱해
   **정규화 저장소(facts)** 에 저장한다. 뷰/기능을 추가할 때마다 그 기능에 맞춰
   원본을 다시 파싱하는 코드를 새로 짜지 않는다. facts는 원본과 동등해야 하며,
   이후 어떤 뷰든 이 facts에서 파생한다.

3. **파싱 단계에서 뷰별 가공본을 미리 만들어 저장 (derived).**
   파싱이 끝나면 통합 분석·호스트 정보·실행 이력 등 각 뷰에 맞게 facts를 조합·가공해
   **별도의 파생 데이터베이스(derived)** 로 저장한다. 예: 실행 이력은 UserAssist,
   Amcache, Prefetch, BAM, SRUM 등을 추출·재조합해 뷰 전용 테이블로 만든다.
   GUI에서 뷰를 클릭할 때 그 자리에서 가공하지 않고 **이미 가공된 데이터를 로드**하므로
   분석이 빠르다.

이 구조는 호스트 디렉터리의 카테고리별 SQLite(facts: `REGISTRY/`, `EVENTLOG/` 등)와
`_OVERVIEW/`(derived)로 구현되어 있다. 별도의 정규화 백엔드 계층
(`HostStorageBackend::NormalizedV1`, `.normalized` 마커)을 도입하려던 시도는
2026-08-28 사용자 지시로 전량 폐기했다(`graveyard/normalized-attempt-2026-08-28`
브랜치에 박제). 그 구조를 되살리지 않는다.

**재파싱 정책 (2026-08-30 사용자 확정):** 호스트의 수집 데이터는 불변이므로 실패한
파싱은 다시 해도 실패한다(파서 기능은 완벽 전제 — 실패 = 손상·오수집 원본 판정).
따라서 재파싱은 이전 결과를 보존하지 않는다: 발행 직전에 이전 결과를 삭제하고
이번 실행 산출물만 발행한다(전체 실행은 전 카테고리, 범위 실행은 대상 카테고리 +
`_OVERVIEW`). facts와 derived는 항상 같은 실행 한 시점의 것이다. 취소된 실행은
발행 전 중단이므로 이전 결과가 유지된다.

### 복구 정책 (사용자 확정)

- **삭제된 데이터는 복구하지 않는다.** 예: Registry의 삭제된 셀(deleted cell) 복구를
  하지 않는다. 할당된(현재 유효한) 레코드만 파싱한다.
- **디렉터리에 함께 수집된 트랜잭션 로그(.LOG1/.LOG2 등)는 적용한다.** 하이브에
  로그를 적용해 최신 커밋 상태를 반영한다. 로그가 없거나 손상·미적용이면 그 사실만
  기록하고 로그 없이 하이브 파싱을 계속한다 — 로그 문제로 하이브 전체를 실패시키지
  않는다.
- 원본 자체가 손상되어 열 수 없는 경우(예: dirty `SRUDB.dat`)는 복구를 시도하지
  않고 실패로 기록한다.

### 일반 규칙

- 증거 폴더 안의 모든 지원 파일을 탐색·파싱한다. 부분 손상, 누락된 보조 파일,
  개별 파일 오류가 있어도 다른 파일과 복구 가능한 레코드는 빠뜨리지 않는다.
- 수집기는 같은 파일을 두 경로에 두지 않는다는 운영 전제를 따른다(2026-08-30
  사용자 확정). 따라서 탐색 단계에 내용 지문 기반 중복 제거를 두지 않는다 —
  발견된 파일은 전부 파싱 계획에 포함되며, 증거가 접혀 사라지는 일이 없다.
- 완전히 해석 불가능한 손상 파일만 건너뛰고, 그 사실·파일·오류를 결과에 기록한다.
  예외 하나로 아티팩트 전체나 파이프라인을 중단하지 않는다.
- 파서는 실행 당시 사용한 원본 증거 파일, 복구 로그 적용 여부, 파일별 추출 레코드
  수를 `parse_report.json`에 저장한다. 대시보드는 이 저장된 보고서를 사용하며,
  화면 진입마다 대형 SQLite를 전수 조회해 정보를 재구성하지 않는다.
- 파생 개요(예: ExecutionHistory)는 원본 SQLite 파일명·테이블·rowid를 포함한
  `record_key`를 저장한다. 원본/개요/타임라인 어디에서 북마크해도 같은 증거
  레코드의 상태가 동기화되어야 한다.
- Registry 트랜잭션 로그, 부분 손상이지만 열 수 있는 SQLite/캐시, JumpList 등은
  복구 가능한 내용을 최대한 파싱한다(열 수 없을 정도로 손상된 원본은 복구 정책대로
  실패 기록). 파일별 결과·복구 여부를 분석가가 확인할 수 있어야 한다.
- Windows 증거의 문자열 인코딩은 원본 포맷을 따른다. 특히 LNK/JumpList는 UTF-16LE
  Unicode 경로와 CP949 ANSI 경로를 모두 지원한다. 기존 저장 결과는 재파싱해야 변경된
  디코딩이 반영된다.
- 느린 파서는 파일 단위 병렬 처리, 스트리밍/배치 삽입, 불필요한 임시 파일·전수 스캔
  제거를 우선 검토한다. 성능 개선이 증거 누락으로 이어지면 안 된다.
- Browser Cache, Browser History, AI 대화 데이터는 대용량을 전제로 한다. 페이지 단위
  조회를 사용하고 AI 대화의 메시지·AI가 공유한 링크까지 추출한다.

### Chromium History의 WAL 처리 (2026-09-22)

- Chrome·Edge·Whale의 `History`는 함께 수집된 `-wal`·`-shm`을 포함해 읽는다.
  보조 파일 목록을 History 처리 전에 고정하고 `parse_report.json`의 입력에 남긴다.
- `immutable=1`로 주 DB만 읽던 구현은 WAL에만 있는 `urls` 테이블을 발견하지 못해
  정상 수집본을 0건으로 처리하거나 최신 커밋 행을 누락했다.
  `1bf5ea5`(2026-08-19 Rust 전환)부터 존재한 결함이며, 8/30 스트리밍 변경에서
  새로 도입된 것은 아니다.
- `browser_history::parse_history_stream`은 산출물 폴더 아래의 독립 작업 폴더에
  DB와 계획된 보조 파일을 복사하고, 복사본을 일반 read-only SQLite로 연다.
  SHM이 없어도 복사본 쪽에서 생성할 수 있다. 정상 반환·오류 반환 시 작업 폴더를 정리한다.
  원본에 체크포인트를 수행하지 않으며, 기존 테이블 스트리밍 저장을 유지한다.
- 검증: WAL에만 존재하는 테이블·행, SHM 없는 수집본의 최신 커밋과 미커밋 제외,
  원본 DB/WAL 바이트 보존 회귀 테스트 통과. CLI 호스트 분석으로 대문자 `HISTORY`와
  `HISTORY-wal`을 탐색하고 facts·BrowserActivity에 같은 방문이 발행되는 것을 확인했다.
  macOS 검증이며, 사용자 Windows exe의 실패가 동일 원인인지와 Windows 실행은 미확인이다.
- SQLite 근거: [WAL 동작 §2](https://www.sqlite.org/wal.html#how_wal_works),
  [WAL 파일 보존 §4](https://www.sqlite.org/wal.html#the_wal_file).
